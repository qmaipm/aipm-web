## 大原则(优先级高于一切细则)

### 原则一:先当专家,再当执行者
用户提出任何要求,**先分析这是什么种类的问题**(品牌/SEO/交互/文案/工程/定位…),
然后站在该领域世界顶尖专家的角度,**先给出专业建议、和用户商量,再动手**。
禁止退化成"用户说什么就做什么":该你拍板的专业问题(如 title 后缀、命名、排版),
直接给方案和理由,不要把选择题丢回给用户;方向性问题才需要用户确认。

### 原则二:设计任何页面前,先查再做
动手设计之前,必须先完成三项调研:
0. **先查我们自己的产品页,确认这件事我们到底怎么做的**（2026-08-07 补,列为第一步）。
   写案例、写服务页涉及「数据怎么进来」「系统怎么对接」这类技术口径时,
   **先 grep `app/(site)/products/` 找到已有的权威表述**,照它写。
   *翻车实录:写视觉案例时我没查,自己编了一个「客户把照片导出给我们,我们不进内网」的交付模式,
   与 `/products/iot` 维度四·视觉感知（视频监控/机器人/无人机四类数据统一接进数据本体）
   和 `/products/fmclaw/ontology`（连接器接入已有系统,不替换不重建）直接矛盾。
   被驳回:「视觉数据是通过我们的数据本体接入的,怎么就成了客户导出呢？」
   真实口径:客户在监控系统侧把预警图片落到**中间数据池** → FMClaw **连接器**从池子里读 →
   接进**行业数据本体** → 智能体判断 → **调用工具箱直接开工单派单**。*
   **编出一个和自家架构矛盾的交付模式,是这套 skill 里最严重的一类错误** ——
   它不是措辞问题,是把产品说错了,而且会同时污染案例页、服务页和 FAQ,清理成本远大于写作成本。
1. **SEO/GEO 策略**:这类页面的搜索意图、目标关键词、结构化数据(JSON-LD)、
   以及面向 AI 引擎(GEO)的可引用性——直接回答式段落、FAQ、清晰的定义句。
2. **同类 AI 企业对标**:其他 AI 公司做不做这个页面?做的话怎么做?
   **尤其是 Anthropic、Palantir、OpenAI** 三家:看它们的页面结构、命名、信息密度、CTA 设计。
最后落地时,wording 一律是**务实克制、陈述事实的 Anthropic 风格,加一点 Palantir 的留白与不啰嗦**。

**已完成的调研结论(2026-07,后续直接复用,不必重查):**
- GEO 有效手段(Google 官方指南 + Princeton 研究):非同质化内容(独家已验证数字、第一手案例)、
  每节首句直接给答案(passage 检索按段取)、FAQ 问答对、干净标题层级、
  正文中可独立引用的定义块(`.fmc-defbox`)、「最后更新」时间戳、robots 显式放行 AI 爬虫
  (GPTBot/OAI-SearchBot/ClaudeBot/anthropic-ai/PerplexityBot/Google-Extended,已入 app/robots.ts)。
- GEO 伪需求(Google 官方辟谣,不要做):llms.txt、为 AI 拆碎内容(chunking)、
  为 AI 改写文案、堆长尾变体页、刻意刷外部 mentions。
- 对标实证:Palantir Foundry 产品页 = 4 组「判断短句标题 + 两句解释」零形容词;
  OpenAI Business = 客户案例前置首屏、卖点配真实产品截图、全页单一 CTA 反复出现。
- 数字纪律的 GEO 理由:独家数字最招 AI 引用;未核实数字被引用后是负资产;
  同一数字全站口径必须逐字一致(AI 会跨页交叉核对)。

## 0. 调性(一切判断的根)

**70% Anthropic + 30% Palantir**:克制、留白、平静陈述事实;"已部署"的真实感、短句即笃定。

- **说人话**。每个词都要过一遍:采购总监、项目经理能不能一眼读懂?
  判断标准:"在 Anthropic 或 Palantir 的官网上,会出现这个词吗?"
- **禁用词**(黑话,出现即改):留痕、管控、门控、流程门控、控制层、收口、赋能、抓手、闭环、拉通。
  替换示例:留痕→有记录 / 管控→管理、管住 / 门控→先经人批准 / 收口→统一在一个地方。
- **禁用**:感叹号、夸大词(最/第一/颠覆/领先/革命性)、emoji、全大写英文大标题+中文副标的 PPT 结构。
- **数字纪律**:只用已核实的数字。当前可用:**500 项目**、**100+ 预制工作流**。任何新数字先问用户。
  **量级词诚实,精确数字不诚实**(2026-08-07 沉淀)。「上千条 / 天」是可辩护的量级陈述;
  把同一件事写成「1,500 条 / 天」并标注「真实客户的预警量」,来源却是一次聊天里的估算 ——
  这是把估算伪造成实测,被追问一次全站可信度就没了。
  规则:**没核实到具体数字时,写量级,不要凑一个看起来专业的精确值**;
  实在没有量级依据,**宁可整句去掉数字** —— 一句站得住的话比一个撑不住的数字有说服力。
  推论:同一指标随客户需求变化很大时(例:重点点位接入日均一两百张、全量接入上千张),
  正文要**把区间和它的前提一起写出来**,而不是取中间值伪装成单一事实。
- 命名对齐行业惯例,不自造大词。先查 Anthropic / Palantir / OpenAI 同类功能怎么叫
  (例:治理页叫 控制台/Console,对齐 Anthropic Console、Palantir Control Panel;
  反例:指挥中心/Command Center——Salesforce 自己都改名了)。

## 1. Wording 细则

- **同一个能力有两种说法时,先去产品页查我们到底怎么做的,再选客户内部能批下来的那种说法**
  （2026-08-07 沉淀,当天被推翻重写一次）。
  顺序不能反:**先查实现,再挑说法**。挑说法只允许在「同一件事的不同表述」里挑,
  不允许为了好批而**编一个我们并不这么做的交付模式**。
  *翻车实录:视觉数据接入,我为了「客户好批」写成「客户自己把照片导出给我们,我们不进内网」。
  这与 `/products/iot` 维度四·视觉感知 和 `/products/fmclaw/ontology` 的连接器架构直接矛盾 ——
  真实做法是:客户在监控系统侧把预警图片落到一个**中间数据池**,
  FMClaw 的**连接器**从池子里读取,接进**行业数据本体**。
  这个做法本身就已经满足「不进客户系统、不接视频流」,根本不需要编。*
  **教训:客户能批的说法,通常产品本来就有;编出来的那条一定和自家架构打架。**
  自查两步:① grep 产品页确认实现;② 把这句话放到客户评审会上,谁会反对、反对什么。

- **全角标点**:中文文案一律用全角 ，：（）(参照页统计:首页 56:0、workshop 65:0、agent-park 47:0,全角:半角)。
  半角 ,:() 只出现在代码、纯英文句和 CSS 里。批量转换时正则的 lookbehind 只认汉字类,**不要把引号并入字符类**(会误伤代码里字符串后的逗号,曾造成 16 个 TS1127)。
- **标题**:句子当标题、平实中文。h2 尽量一行(`white-space:nowrap` + 窄屏兜底)。
  句号规则:名词短语式 h2 不带句号;**判断句式双短句 h2 可带句号**,但只适用于
  **陈述产品属性的判断句**(Palantir Foundry 实证:"No Duplication." "Collaboration, Supercharged."
  ——宾语是产品的能力与事实;本站实例:「不是演示。已经在真实项目中运行。」)。
  **禁止作者腔格言当 h2**:议论世事难易、択情、金句体都不行——Anthropic 从不用
  格言当标题,标题只说产品能做什么、为谁做(反例,已下线:「跑通一次不难。难的是每天稳定地跑。」
  ——这是作者在议论,不是产品在陈述)。
- **正文**:中文行高 ≥1.7,正文 ≥16px。`<b>` 只加在真正的结论句上。
  **行宽以汉字计,不以字符计**:叙事型正文 **约 36 汉字/行**(`max-width:36em`),
  66 字符是绝对上限、不是目标(2026-07 实测:案例页原为 64 汉字/行,严重串行;
  Anthropic 案例页 715px / 20px ≈ 36 汉字)。卡片、流程、表格等结构化组件不受此限,继续满宽。
  落地方式:在页面 wrapper 上定义具名变量(如 `--cf-read`)并加注释说明依据,
  **不要写裸 max-width 数字**——具名变量+注释才拦得住后人"顺手改大"。
  **栏宽变量必须用 px,不能用 em**(2026-08-07 事故,被用户当场抓到):
  `em` 在 `:root`/wrapper 上定义、在组件上消费时,按**消费处各自的字号**解析——
  `36em` 在 18px 正文上是 648px,在 13px 的合规小字(`.cf-note`)上只有 468px,
  在 17px 摩擦块上是 612px,15.5px FAQ 答案上是 558px。
  同一页四种「阅读栏宽」,小字组件缩成一条,和旁边 648px 的正文参差不齐,PC 上非常难看。
  这问题在共享壳里,所有案例页普遍存在,而視覺門只量正文行宽、量不到组件间的对齐。
  规则:**「同一个视觉栏」的宽度必须是同一个绝对值**;em 只该用于「随字号缩放才对」的场景
  (如 `.cf-fr-row` 的 dt 定宽跟着标签字号走),不该用于跨组件对齐的版面栏宽。
- **单句 ≤60 汉字**。超过就拆,或改成结构化组件(见 §3c)。破折号 `——` 全篇 ≤2 处,
  「不是…而是…」全篇 ≤1 处:这两个句式一多,读者就在读作者的情绪而不是读事实。
- **FAQ 写法**:用买家的真实问题当 q(出了错谁负责?怎么防越权?能查到哪一步?数据会不会串?能不能随时叫停?),
  a 第一句先给直接答案(人负责。/能。/不会。/可以。),再展开一两句。
- **权限/安全类叙述**:学 OpenAI 的三档式人话——"直接执行 / 先经人批准 / 全程有记录",每档配一个"例:"。
- **页面 title 后缀规范**(全站已统一,新页照执行):
  - 公司/内容/服务/解决方案类页 → `… | 启盟科技`(半角竖线+空格)
  - 产品与能力类页 → `…｜FMClaw™ + 一句定位`(全角竖线,例:`控制台（Console）｜FMClaw™ 智能体安全、权限与审计`)
  - 不叠加双后缀(❌ `… — FMClaw™ 加速营 | 启盟科技`),不用 `— 启盟科技` / `- FMClaw` 等变体
  - description 自然嵌入 SEO 词(智能体治理、AI 权限管理、审计日志等),不堆砌。
- 结尾 CTA 用一句有态度的短句(例:"让智能体进核心业务之前,先看看它怎么被管")。

## 2. VI(硬约束)

- **品牌渐变**:`linear-gradient(115deg,#0070FF,#12B98A)` 蓝→绿。主按钮永远用它(`--brand-grad`),内页主题不得覆盖。
- **单一字族**:Noto Sans SC / 系统栈。页面 CSS 里**禁止任何 `font-family` 声明**。性格靠字号/字重/字距。
- **强调色只蓝绿**。不得出现金/紫/粉等暖色(唯一例外:首页 `--human` 琥珀 = "人做最后决定"语义)。
- **现行标准是冷调平台色板,不是暖米纸底**。三个参照页均如此:首页 `.solhome`、workshop `.solws`、agent-park `.solbd`,
  都是 白纸 `#FFFFFF` / 雾灰 `#ECF3F1` / 深墨绿 `#0B1714` + 蓝绿渐变。
  `globals.css` 里的暖米纸底(`--ivory:#F4F1E8` body 底)是历史遗留,被每个改版页的 scoped wrapper 覆盖;
  **新页面不用暖米纸底**,DESIGN.md 中暖纸时代的描述按历史文档看待。
- **冷调平台色板**(所有新页,scoped 在页面 wrapper 上):
  ```css

  /* 暗场上的强调绿 */ #3fd9b8;  /* 暗场浅绿链接 */ #9fded0;
  /* 暗场正文 */ #AEBAB5;  /* 暗场 lead */ #D7E2DD;
  ```

## 3. 页面结构原则

- **约 30% 留白**。段落 padding 104px(移动 76px),不密排。
- **斑马纹**:相邻段落背景必不同(白 `--paper` / 雾灰 `--mist` 交替),在 markup 手动交替,不用 nth-of-type。
- **全页只留一处暗场**(`--core` 深墨绿),给最有分量的一段(签名段)。
- 章节走 编号 eyebrow(01/02/…,渐变短杠)→ h2 → 正文/组件 的节奏。
- 组件优先复用 `capability.css` 共享件(见 §5),没有再新造。

### 3a. 总览页专则(2026-07 对标 Claude Enterprise / Palantir Foundry 后确立,严格执行)

总览页是**编排层,不是内容层**:它的职责是 论点→地图→证据→入口,内容本体留在子页。

1. **子页正文禁止复制到总览页**。同一张产品截图、同一段详情叙述,全站只在一个页面作主视觉;
   总览页只给一句定位 + 入口(反例,已修:工作流编辑器截图曾同时出现在总览页与 workflow-engine 子页)。
2. **同构卡片网格全页 ≤2 次**。每个主段落要有专属版式(对标 Claude Enterprise:logo 墙→三列→checklist
   面板→引言+指标→暗场视频→代码演示,无一重复);同一套卡片模板连用 3 次 = 设计失败。
3. **信任主张必须用 checklist 面板 + 具体能力清单**(Anthropic "Made to pass security review" 范式:
   独立面板 + 逐项 ✓ 可核对能力,本站实现:总览页 `.fmo-trust` 面板)。准确/一致/安全这类主张
   禁止用三张小字卡打发——大 B 买家要的是可逐项验证的清单,不是形容词。
4. **h2 禁作者腔格言**(见 §1 句号规则:句号只给产品属性判断句,不给议论难易的金句)。
5. **LinkCards 每页 ≤2 组**。入口优先融进段落本体(卡片本身可点、段尾一行箭头链接、chip 带),
   不靠末尾追加链接卡堆叠(反例,已修:总览页曾有 6 组 LinkCards)。
6. **配图铁律**:证据用真实产品界面,不用摆拍照片;概念用统一风格的等距 3D 插画
   (蓝绿渐变 #0070FF→#12B98A、浅薄荷底、无文字);重磅页面不吝恾插图,但每张图必须有信息职责,
   装饰性配图一张都不要。
7. **禁止孤儿卡片**:任何卡片网格,每行只能是 2 张或 3 张,4 张必须走 2×2 两行;
   **绝不允许 N 张卡片排成 "3+1" "2+1" 这类末行单卡孤悬的版式**(反例,已修:
   workflow-engine §07 曾 4 卡排成 3+1)。写卡片组前先数数量:1 张→横向大卡(solo),
   2 张→一行两列,3 张→一行三列,4 张→2×2,5 张以上→重新想信息架构,不是塞网格。
8. **场景/案例互链必须带插图**:凡是链去 `/scenarios/*`、`/cases/*` 的互链卡,
   一律用 `_shared.tsx` 的 `ScenarioCards`(插图 + 标签 pill + 标题/描述/箭头),
   **禁止用纯图标 LinkCards 承载场景或案例链接**。平台层级互链(工具箱/控制台/
   数据本体等能力页之间)才允许继续用图标 LinkCards。场景插图存
   `public/products/fmclaw/scenario-*.webp`(1100×614,等距 3D、蓝绿限定色)。

### 3b. 产品信息架构三分法(2026-07 对标 Anthropic / Palantir 导航后确立)

导航与页面里的"产品",必须严格区分三类,**不得混编**:

1. **自研产品线**(公司自己造的东西):FMClaw™ 平台、IoT 物理世界感知、机器人与智能装备。
   导航产品栏只按自研序列分组(对标 Palantir 营销导航只放 AIP/Foundry/Gotham/Ontology/Apollo 五个自研平台)。
2. **平台能力**(某条产品线内部的层):数据本体/工作流引擎/工具箱/控制台,归在所属产品线组内。
3. **第三方兼容**(接别人家的东西):钉钉/飞书/企业微信协同属于**工具箱(连接器)的能力范围**,
   在导航里只是平台组末尾的一个条目,**永远不单设导航组、不单设产品板块**
   (对标 Anthropic:Connectors 只是 Platform 下拉 "Works with Claude" 组里的一行;
   Palantir 的第三方连接 Data Connection 甚至只出现在文档,营销导航完全不放)。

落地规则:
- 总览页不给第三方兼容开独立 section;降级为所属层(L3 工具箱)行尾的横向兼容带(`.fmo-ecoband`:
  渐变左沿 + 左文右图 + 平台名 chips,整卡可点)。
- 暗场签名段只讲一件事,不许把"兼容性 + 自研产品入口 + 开始方式"三种诉求塞进同一暗场
  (反例,已修:总览页 §07 曾以「不替换现有平台」作标题下挂协同/IoT/机器人三卡)。

### 3c. 客户案例页专则(2026-07-25 审计 + 对标 Anthropic / OpenAI / Sierra 后确立,严格执行)

**这个板块的目的不是秀肌肉,是让访客找到一个有说服力的、可参照的同行最佳实践。**
读者进来只问三件事:这案例解决了什么问题?能帮我干嘛?AI 在里面到底做了什么?
三个问题任一答不上来,页面就是失败的——写之前先自检这三句,不要先写文采。

**四段式结构(11 篇已统一,新案例照抄,不要自创段名):**
`成果概览` → `客户面临的问题` → `AI 做了什么` → `结果`
- eyebrow 必须直答读者的疑问。**禁止**「启盟帮 X 实现了」这类以我方为主语的自夸式 eyebrow,
  也禁止「接入之后」这类只讲时序、不讲内容的空段名(两者均为 2026-07 已下线写法)。
- 每篇结尾给一句"什么样的企业适用",让读者能对号入座——这是"可参照"的落点。

**硬指标(`scripts/cases-lint.mjs` 逐条把关,CI 门禁,不许绕过):**

| 项 | 上限 | 为什么 |
|---|---|---|
| 正文字数 | ≤900 字 | 信息密度过高读者直接弃读 |
| 单句 | ≤60 汉字 | 曾出现 212 字长句,读到句尾忘了句首 |
| 破折号 `——` | ≤2 | 一多就变成作者在抒情 |
| 「不是…而是…」 | ≤1 | 修正式句型是自我辩解的语气 |
| CaseWins | ≤4 条,每条 ≤30 字 | 首屏要能一眼扫完 |
| AI 首次出场 | 全文前 15% | 读者要立刻知道 AI 干了什么 |
| 同一数字重复 | ≤3 次 | 重复不等于强调,等于啰嗦 |

**AI 首次出场位置按读者真实阅读顺序算**(含 CaseWins 等渲染在正文之上的组件),
不是按正文段落算——否则会严重低估读者实际多久才见到 AI。

**长句一律改成结构化组件,而不是硬切成两句:**
- `CaseFlow` — 真实有序的管道(定标准→管执行→评质量→做优化;到场→执行→核对→预警)
- `CasePoints` — 并列要点(三层能力、三类难处),2×2 网格
- `CaseNote` — 政策依据、服务期、口径说明。**这类内容永远单独放,禁止当叙事插入语**
  (曾把 152 字的政策引用塞进客户问题段,是句子失控的头号原因)。
  **「单独放」指的是独立成块,不是放到 CaseSection 外面**(2026-08-07 沉淀):
  它必须仍在某个 `CaseSection` **内部**、紧跟它说明的那段正文。
  *翻车实录:视觉案例把 CaseNote 放在两个 Section 之间、直接挂在页面根下,
  结果它脱离正文栏横向铺满 1440px 视口(正文栏才 648px),lint 与视觉门全绿都没拦住。*
  `.cf-note` 的栏宽约束(`max-width:var(--cf-read)`)写在 `.cf-sec-body>` 选择器上,
  组件放错层级样式就整个失效——**新组件写完先量 bounding box,别只看类名挂上没有**。
- `CaseQuote` — 暗场客户原声,全页仅一处

**H1 与 summary 分工(不许互相重复):**
- H1 = `客户身份：AI 做了什么，带来什么结果`(30–40 字)。三个成分缺一不可。
- summary = 60–80 字,**补 H1 没说的买家情境**(上线前的配置、监管要求、失败的老办法),
  不复述 H1 已有的结论。summary 同时喂 hero lead,写的时候按 hero 第一段读一遍。
- 改 `cases.ts` 的 title / summary / cardMetric 前先 grep 消费方:
  列表卡片、相关案例、hero、`pageMetadata`、Article JSON-LD 共用这几个字段。

**数字纪律:** 案例数字一律走 `docs/SEO-GEO-STRATEGY.md` §4a 白名单**逐字复用**,
§4b 禁用数字与已退役口径绝不出现。拿不准的数字不写,不要自己换算或估算。

**排版与信息层次(2026-07-25 第二轮落地,新案例照此):**
- **散在正文里的数字对比,一律改成 `CaseCompare` 前后两列表。**

  表格能一眼扫完。改表之后正文只留**结论句 + 一条最值得说的解读**,不要复述表格里的每一行。

  定责从「靠回忆」→「对着当天记录」)。但**凑不出真实对照就不做表**,不要为了版式造对比。

### 3d 案例可信度:说服力不来自数字多,来自读者敢照着做(2026-07-25 沉淀)

以访客身份通读 11 篇案例后的结论:「能找到自己」「看清方向」都成立,但「想联系」不成立。
断点不在版式,在**缺少读者视角的三样东西**。这三条是案例板块的验收标准,不是可选项:

- **每篇必须有 `CaseFit`(适用性判断),且 `unfit` 不可为空。**
  读者读完「结果」的下一秒问的是「这个在我这儿成立吗」——这个疑问要在**案例页当场**被回答,
  不能只放在列表页 FAQ 里(疑问发生的位置和答案的位置必须重合)。
  `unfit` 写真实前置条件(口径没统一、外包合同没约定数据交付、团队不接受核验),
  不写「规模太小不适合」这种敷衍。**敢写不适用,可信度才高于一份战报。**
  已由 `cases-lint.mjs` 强制:缺 `CaseFit` 或 `unfit` 为空即 fail;每栏 ≤3 条(再多就从判断退化成清单)。
- **每篇要有「投入侧的事实」(`CaseFit` 的 `cost`)。**
  通篇讲我们做到了什么,却不讲读者要付出什么,是最大的洞。
  只写案例里确有其事的:不换平台 / 沿用现有团队 / 在原预算内启动 / 无需二次开发 /
  需要 IoT 投入 / 按月才见效。**降低读者的成本比抬高我们的成绩更能促成联系**;
  没有事实就不写,绝不为了版式凑第三条。
- **CTA 必须一重一轻两扇门。** 只留「预约加速营」等于把「有点想聊但还在内部说服阶段、
  不想被销售跟进」的人挡在外面 —— 意愿有、落点无。
  轻门给 `/contact`(先问一个问题)+ 电话,`.endcta .cta-btns` 承载并排按钮,窄屏竖排。
- **零摩擦是「秀肌肉」的真正来源。** 11 篇全胜、过程全顺,物业老兵会默认折价一半来读。
  真实摩擦(前两周数据是乱的、哪个环节比预想难、后来改了做法)需要客户素材,**不许编**;
  没素材就宁可留白,`unfit` 已经承担了一部分诚实度。

排版约束:`CaseFit` 固定 `cf-band mist`(位于「结果」与「相关案例」之间),
所以**11 篇的「结果」一节必须走白底,不要加 `mist`**,否则两段 mist 相连、斑马条纹断。
`.cf-h2` 是 24ch 限宽,该节标题控制在 12 字内(「适合谁,什么情况下不适合」),否则末尾甩出孤字。
右栏刻意不用红色:它不是错误提示而是前置条件清单,只有左栏带 VI 绿(维持蓝绿双色)。

其他两条沉淀:
- **禁用词是子串匹配,会误伤正常中文。**「验收口径」里含「收口」。
  `cases-lint.mjs` 的 `BANNED_SAFE` 用来挖掉确定无害的词组 —— 是修检查器,不是改正确的中文。
  新增例外必须真的是正常词,不能拿它给禁用词开后门。
- **`cases-visual-check.py` 首访要允许重试一次。** 服务刚起来第一个页面冷编译常超 60s,
  那是环境慢不是页面坏;第二次仍失败才算真问题。
- **视觉门的 slug 列表必须从文件系统自动发现,不许写死**(2026-08-07 沉淀)。
  写死的 11 个 slug 漏掉了新增案例,「视觉复验通过」对新页面是空话——
  CaseNote 铺满全屏的排版事故就是这么漏过去的。已改为扫 `app/(site)/cases/*/page.tsx`。
  这和 §3g 第 7 条(GROUPS 写死漏新案例)是同一类坑:**凡是靠人工维护的清单,
  新增条目时一定会被漏掉一次;能从事实来源推导的清单就不要手抄。**

### 3e 摩擦叙事与监管词禁令（2026-07-27 沉淀）

**监管机关名称一律不写进对外物料。** 用户口径，无例外：

> wording 要经得起审计：只是要提交被查。不要把公安、司法这些写在官网，这是很大的忌讳。

即便客户确实每月接受某机关核查，官网也只写「外部核查」「第三方核查」「提交核查」。
点名机关既抬高审计风险，也把客户置于不必要的曝光下。
`cases-lint.mjs` 的 `BANNED_REGULATOR` 已强制（公安/司法/警方/派出所/执法/检察/法院）。
**注册表 `cases.ts` 要单独扫一遍** —— 标题、summary、seoTitle、metaDescription、FAQ 都住在那里，
这些字段直接进搜索结果和 AI 引用，风险比正文更高，只扫 `page.tsx` 等于把最危险的位置留成盲区。

**摩擦一节（`CaseFriction`）—— 可选，但写了就要真。**
三段式：起初以为 → 实际发生 → 后来怎么过的。位置在「AI 做了什么」与「结果」之间，
**读者看到成绩之前先知道代价**；放在结果之后会读成事后找补。

- 只写客户口述里确有其事的。**编造摩擦等于伪造证据，比不写更坏**；
  客户明说「没有摩擦」的案例（如西门子危化区域）就不放这一节，组件本身可选。
- 每段 ≤80 字，全节 ≤200 字。摩擦一旦写长就变成公关稿，写短才像人话。
  `cases-lint.mjs` 的 `frSeg` 已强制。
- **降敏是硬要求。** 公开官网，客户圈内会对号入座。涉及个人与追责的事实
  （怠工、裁员、某供应商不配合）一律上移到岗位/层级/「其中一方」的抽象度：
  「部分岗位人在班上，实际服务量却远低于配置」而不是点名怠工；
  「编制要调整，班组长、经理、总监各有各的顾虑」而不是写裁汰。
- **降敏不等于可以模糊事实本身。** 抽象的是「谁」，不是「是什么」。
  一稿把用户口述的「怠工」误记成「代工」，写成了「实际到岗情况与登记不符」——
  代工是人不对（别人替他干），怠工是量不对（人在岗、活没干），指向的问题完全不同，
  而且与该案例正文「砍掉的是错配和空转」自相矛盾。
  **涉及事实定性的词，拿不准就回问用户，不要顺着语感猜。**
- `resolution` 不许写成圆满。留一句「这一步绕不过去」比十句成功更可信。

**行业洞察（值得反复用的论点，来自用户）：**
国内 FM 最大的结构性 bug 是**服务标准由乙方定**。标准不在甲方手里，
就无法客观衡量工作量、也无法保证设施设备运维安全。多个案例的摩擦本质上是同一件事：
标准归属权从乙方转移到甲方。这条可以作为案例板块的暗线，但要落在具体案例上讲，不要单独说教。

**排版：`CaseFriction` 固定 `cf-band mist`。**
最初想走白底、靠左侧竖线自行区分，视觉门当场判定与上一节「AI 做了什么」同色、斑马断了。
教训：**「自己看着有区别」不等于版面有节奏，底色交替才是。**
`.cf-fr-row` 的 `dt` 定宽 5.6em（「后来怎么过的」6 字不折行），640px 以下改上下堆叠 ——
并排时中文正文只剩十几字一行，读起来是断的。
只有 `is-out` 行加重：它是读者真正要抄走的东西，前两行是背景，三行同权重会打架。
`cases-visual-check.py` 已加 `dtWrapped` / `ddEscaped` 检测（lint 看不见折行）。

### 3f 案例配图（2026-07-27 立，2026-08-07 推翻重写）

**案例页要配图。** 案例讲的是现场发生的事，纯文字读者只能听我们说；
一张图能让他看见现场长什么样，这本身就是说服力的一部分。

> **2026-08-07 推翻旧版。** 旧版写的是「默认不配图，示意图一律禁用」，被驳回：
> 「没有这个说法，案例页怎么就没配图了？」
>
> 复盘错在哪 —— 旧版的**事故是真的，适用范围被写错了**。真实发生的只有一件事：
> AI 放大把界面截图里的日期 `2026-06-01` 改成了 `2020-00-01`。
> 这件事只能证明「不许 AI 动证据图的像素」，我却把它推广成了「所有图都别放」。
> **教训写进 skill 时，必须连它的适用边界一起写。**
> 一次具体事故只能约束它真正涉及的那一类对象；扩大成普遍禁令，
> 规则就会开始禁掉正确的事 —— 这条比配图本身更重要。

**按图的性质分成两类，规则完全不同。分不清这两类，就会既不敢配图、又会伪造证据。**

**一、证据图 —— 产品界面截图、现场识别结果原图。像素一个都不能改。**

- **不许 AI 放大、不许 AI 重绘、不许 AI 修字。** 界面里的日期、数字、驳回理由都是证据，
  模型重绘时会把它们改掉（实测把 `2026-06-01` 写成 `2020-00-01`）。**改字等于伪造证据。**
- **显示宽度 ≤ 原图像素宽度的一半。** 界面小字在 Retina 下要 2 倍原生像素才不糊。
  原图 1024px → `maxWidth: 512`，实测有效 DPR 2.00。宁可小而清楚，不要放大到糊。
- 拿到图先量原始像素，**如实告诉用户这是几倍图**。1 倍图能用，但显示尺寸被锁死。
- 降敏只能用**打码、裁切、遮挡**这类不改内容的手段，不能让模型「重画一个干净版本」。
  车牌、人脸、门牌号、真实客户名必须处理掉。

**二、场景图 —— 生成的现场还原，用来让读者看懂这件事发生在什么环境里。允许，但有三条硬线。**

- **图注必须让人知道这是还原，不是截图。** 不冒充证据，就不算造假；
  冒充了才是。写法：「场景还原：……」。
- **画面里不许出现可读的界面文字、数字、指标、品牌标识、人脸、车牌。**
  这些东西一旦出现在生成图里就是伪造的证据 —— 生成图只能还原**物理现场**
  （场地、设备、光线、空间关系），不能还原「我们的系统」和「客户的身份」。
- **只还原正文里确实写了的事。** 正文说的是充电区里一辆车在冒烟，图里就只能是这个；
  图不能比正文多讲一件事。

**三、封面图 —— 和正文场景图是两类东西，规则不通用。**（2026-08-07 沉淀）

- **封面先服从全站一致性，再考虑单篇好看。** 封面同时出现在 `/cases` 列表页上，
  十几张排在一起，任何一张风格不同的都是视觉噪声。
  写新案例前**先看一遍 `public/cases/cover-*.jpg`**：现存全部是**真实暗场纪实照**
  （现场、设备、弱光、无文字），那么新封面就只能是这个语言。
- **抽象插画、发光图形、渐变色块一律不进封面。** 即使单看不难看。
  *翻车实录：我给视觉案例做了一张深蓝/青绿发光矩形的抽象插画，
  是全站 12 张封面里唯一一张非实景图 —— 被驳回：「案例页都是真实的场景图，你加了一个什么图？」*
- **规格对齐现存文件，不自己定。** 量一张现存封面的尺寸和体积再产图
  （当前基准：1264×711，JPEG q84，110–145 KB）。
- 生成封面同样受第二类的三条硬线约束（无可读文字、无品牌标识、无人脸车牌）。
  **自审一定要放大看车身、墙面、地面** —— 模型爱在这些地方补品牌字样和纸质标牌。
  发现问题用 **image-to-image 传原图修**，不要文生图重来（构图会跑）。

**内容匹配优于位置好看。** 图放进哪一篇、放在哪一节，取决于它和那段正文说的是不是同一件事
（那张审批台截图写着「A栋10层卫生间点位质检异常」，所以它属于 restroom-quality）。
位置：紧挨它解释的那段正文，不为了版面均衡而挪。

**图注是正文的一部分，不是标题。** 左对齐、与图等宽、13px 弱色；
内容要讲**这一张图里发生了什么**（「AI 读完 8 条待审后驳回了 1 条 —— 复检照片里地面
仍有积水」），不要写成「系统界面示意」这种空话。居中图注在左对齐的正文流里会显得飘。
场景图的图注还要多承担一件事：**说清它是还原**（见上文第二类的第一条硬线）。

**窄屏：`.cf-fig` 必须有 `max-width:100%!important` 兜底**，
否则内联 `maxWidth` 会超出视口造成横向滚动（视觉门的 `docWidth` 会抓到）。
390px 实测收到 346px、无横滚。窄屏下界面小字确实读不出 —— 这是可接受的分工：
手机上图只负责"存在性证明"，信息由图注承担。

**lint 必须扫 `alt` 与 `caption`。** 图注常被当成"顺手写的说明"而漏检，
恰恰是最容易夹带旧口径、旧数字、监管机关名的地方。`cases-lint.mjs` 已加 `CaseFig` 提取。

### 3g 场景标签:用买家的原话,不用我们的术语（2026-08-06 沉淀）

场景标签不是分类学作业,是**流量入口**和**自我辨认开关**。判断标准只有两条:
**① 用户能搜到（引流）② 进来一眼认出"这就是我要找的"**。分类是否优雅,不在考核项内。

**硬约束（录入新案例时逐条过）**

1. **每个标签至少挂 2 篇。** 只挂 1 篇的不是"场景",是"这一篇的特色" ——
   写进标题或 `cardMetric`,不许占一个筛选维度。孤儿标签的筛选价值为零:
   点进去只有一篇,等于让用户白点一次。
   *2026-08-06 审计:19 个旧标签中 12 个只挂 1 篇（孤儿率 63%）,场景索引形同虚设。*
2. **标签总数凑满 3 的倍数。** 场景索引区是 3 列网格,落单会出现孤儿卡（同 §3c 卡片规则）。
   现为 9 个 = 3×3 满格。加标签就一次加 3 个,不够就先并进已有标签。
3. **每个标签必须先用真实搜索验证过**,再写进 `CASE_TAGS`。验证方法见下。
4. **标签总量不无限增长,新案例优先挂现有标签**（2026-08-07 补）。
   用户原话:「你标签不可能无休止地增加,对不对？我也没见过无休止增加的标签。」
   录新案例时**先算,再决定**:现有标签是否已满编（每个 ≥2 篇 且 总数 %3==0）。
   满编时新增一个标签会**同时破两条约束** —— 总数不被 3 整除、新标签只挂 1 篇成孤儿。
   此时正确做法是把新案例映射到**两个已有标签**上,并在 `CASE_TAGS` 里写清映射理由。
   *实例（2026-08-07）:视觉案例本可新开「安保」,但 9 个标签已满编,
   于是挂「不知道现场到底怎么样」（摄像头装了一堆没人看得完）
   + 「巡检走过场」（设备间与 VIP 区域的状态识别）,两个都对得上正文事实。*
   要加就一次加 3 个,且每个都得有 ≥2 篇撑住。
5. **一篇案例可以挂多个标签,不为「看起来干净」砍。** 一篇案例会被好几种不同的人搜到 ——
   工厂那篇同时是"供应商管不住""保洁质量不稳定""人手不够"三类人的答案。
   为了"看起来干净"砍标签,砍掉的是发现路径。
6. **每篇案例至少挂 2 个标签、且全部案例 100% 覆盖**（当前 12/12,数量随新案例递增）。
   零标签的案例在场景索引里直接消失,等于白写。
7. **注册进 `cases.ts` 不等于上线**（2026-08-07 补）。`/cases` 列表页的分组
   （`GROUPS[].slugs`）是**写死的数组**,新案例不落进任何一组,列表页上就找不到它 ——
   页面能打开、注册表齐全、lint 全绿,但唯一入口只剩站内链接。
   *当天就漏在这里,靠人工数列表页链接数（11 ≠ 12）才发现。*
   已在 `cases-lint.mjs` 补上双向校验（案例目录 ↔ 分组 slugs）,新增案例必须同时落一个分组。
8. **落哪个分组要靠搜索验证「谁在问这个问题」,不许看标签里有没有相同的字**（2026-08-07 补）。
   `/cases` 的分组是**读者身份**（「如果你在物业集团负责经营或数字化」),不是话题分类。
   判断动作:把案例回答的那个问题,分别按两三种候选身份搜一遍,看谁在正面问这件事。
   *翻车实录:视觉案例我塞进「如果你负责医院、轨道交通或危化区域这类高安全等级场景」,
   理由只是那一组名字里有「安全」二字 —— 案例本身是智慧园区,和医院/轨交/危化毫无关系。
   被驳回:「这个用户标签是什么意思？你动脑子了吗？」
   补做搜索后结论清楚:物业侧内容正面打这个问题（行业白皮书写「摄像头接入 AI 分析」、
   物业小区安防采购、园区平台对接视频监控),行政侧则是「参与智慧园区管理」的宽口径框架,
   安全只是其中一格。所以归 `for-group`(物业集团)。*
   **词面相同不等于人群相同。** 挂错分组的代价是:搜进来的人一眼看不到这是他要找的东西,
   等于白引流。

**选词方法:每个候选词当成搜索词真搜一遍,看搜索结果是谁**

- 搜出来是**同行在卖方案** → 真实买家需求,收（有人花钱买流量的词,就是有人在搜的词）。
- 搜出来是**别的行业占着这个词** → 弃。语义被劫持,排不上去也接不住。
  - `扭亏为盈` → 上市物企财报新闻（碧桂园/融创服务/雅生活）。作为**正文里的结果陈述**没问题,
    作为**搜索入口标签**接不到人。
  - `智能问数` → BI/ChatBI 产品（SQLBot/火山方舟/钉钉宜数）。
- 搜出来是**终端用户/业主在抱怨** → 弃。`业主投诉` 搜到的是 12345、街道办、"能不能拒缴物业费",
  搜的人不是我们的买家。
- 搜出来**没有任何解决方案内容,只有招标文件和论文** → **最该收**。
  这是未被满足的需求,而我们有案例能答。按 Princeton GEO（KDD 2024）,
  弱势方在这类词上的杠杆最大（rank-5 +115.1% vs rank-1 −30.3%）。
- 搜出来**首页全是供应商在讲自己的技术路径** → **看买家的卡点有没有人回答**（2026-08-07 沉淀）。
  这是上一条的加强版判据。判断动作两步:
  ① 搜品类词,看首页在讲什么 —— 若清一色是厂商介绍自己怎么实现（接视频流、装算力盒子、换 AI 摄像头）,
  说明这是**供应商视角的红海**,我们进去只是第 N 个讲技术的;
  ② 换成**买家真正卡住的那句话**再搜一遍 —— 若结果只剩法条与合规文章、
  没有任何厂商在正面回答,那就是**空位**。
  *实例:搜「AI 视觉识别」全是算法厂商在讲自己的模型;
  换成买家的卡点「监控预警一天上千条没人看得完」再搜,厂商都停在「识别准不准」,
  没人回答「识别完了谁去处理」。所以词面取「预警没人看得完 → 识别完直接派单」,
  不取「AI 视觉识别」。*
  **词面必须落在我们真实的差异上。** 上例的差异不是「识别得准」（算法厂商都会讲）,
  而是**识别之后的联动**:数据进数据本体 → 智能体调用工具箱 → 直接产生业务动作(开工单、派岗位)。
  选词前先问:这个词面指向的能力,竞争对手能不能照抄一句话。能抄,就还没找到差异。
- 我们自己的产品术语一律弃:`AI 降本增效`/`提质增效`/`IoT 数字化`/`人机协同`/`数据治理`
  —— 没有买家会这么搜,这些词只在我们的 PPT 里存在。

**归属必须有正文证据,不许凭语感挂。**
挂标签前在案例正文里 grep 到对应的事实或数字才算成立。
例：医院那篇挂"报修响应慢",凭据是正文里的"工单及时接单率 24%→95%";
卫生间那篇挂"人工成本降不下来",凭据是"巡检人力下降约 60%"。
挂不上凭据 → 说明这篇答不了这个问题,别挂。

**术语 → 买家话（2026-08-06 换过的对照,后续沿用同一风格）**

| 我们原来的词 | 买家实际搜的话 |
|---|---|
| 设备巡检、设备安全 | 巡检走过场 |
| 外包管理 | 供应商管不住 |
| 品质管理、服务标准量化 | 保洁质量不稳定 |
| AI 降本增效、扭亏为盈、提质增效 | 人工成本降不下来 |
| 人机协同、清洁机器人 | 招不到人、人手不够 |
| 报事报修、智能工单 | 报修响应慢 |
| 合规核查、双人双岗巡查 | 检查记录经不起查 |
| 自动运营报告、数据治理、智能问数 | 不知道现场到底怎么样 |
| （新增,原先无入口） | 多项目管不过来 |

**呈现方式:服务端渲染的链接,不做客户端筛选。**
案例列表页是纯 server component,加 `useState` 会把整页变成 `"use client"`;
且 AI 爬虫不执行 JS —— 藏在交互后面的内容对 GEO 等于不存在,
筛选结果也没有 URL 可被索引。所以场景索引区（`.ca-scenenav`）是
**直接渲染出来的 `<a>` 列表**,每个场景下列出案例的行业 + 关键数字。
同一批标签同时以 chip 形式出现在卡片上（`.ca-scenes`）——
索引区负责"按问题找",卡片 chip 负责"扫到时认出"。
也**不要**为每个场景开聚合页（违反 §7b 伪需求禁令）。

**改 `CASE_TAGS` 必跑的验证**（顺序固定,少一步不算完）

1. 孤儿/覆盖脚本:标签数 %3==0、每标签 ≥2 篇、每案例 ≥2 标签、全部案例 100% 覆盖、`USE_CASE_ORDER` 与实际一致。
2. `node scripts/cases-lint.mjs` —— `getRelated` 靠 `CASE_TAGS` 打分,改标签会重排全部 11 页的相关推荐。
3. `python3 scripts/cases-visual-check.py`
4. **亲眼看渲染截图**（桌面 1440 + 移动 390）,不许靠读 CSS 判断换行。
   *2026-08-06 就是靠截图才发现最后一行剩一张孤儿卡,进而发现"投诉多"是症状不是场景 ——
   它挂的两篇已被别的标签覆盖,不提供新的发现路径。删掉后正好 3×3 满格。*

### 3h 视觉层级:数字是视觉元素,不是文案（2026-08-06 沉淀）

案例列表页的场景索引区第一版被驳回（原话：「页面视觉设计太烂了吧」）。
复盘后确认：问题不在配色细节，在**一个结构性错误**——
目录借用了案例卡的视觉语言（白底+圆角+描边盒子），于是 9 个导航盒子
和 11 张真案例卡视觉权重相同，全页没有主次，读起来像 sitemap。
以下五条是修复后确立的硬规则。

**① 一页只保留一种卡片语言。**
真内容（案例卡）才有资格用卡片；目录、索引、导航一律回归**排版**——
整宽行 + 发丝线分隔。附带好处：横排行天然等高，
2 条和 4 条的行都不会留下盒子底部的空洞（第一版参差不齐就是这么来的）。

**② 数字上位当视觉锚点,不要用图标。**
索引里每一条**数字打头**（`414 项标准建模`），下面一行小字才是它属于谁
（`医疗健康（国际医院）`）。学 Stripe /customers（巨大数字 + 一行注脚）
和 Vercel /customers（标题本身就是结论+数字）。
**不要给抽象问题配抽象图标** —— 9 个抽象图标属纯装饰，撞 §3f「默认不配图」，
也撞 2026 SaaS 拆解里的已死模式（抽象插画、图库照片、长标题）。
数字比图标更有说服力，且零维护。
数字字段要单独存（`navMetric`，≤16 字、必须含数字），不要复用长的 `cardMetric`——
长文案横排会折行，把整片对齐弄乱。lint 已卡这两条。

**③ 元数据不许穿强调色。**
行业·规模·城市是注脚，用弱灰（学 Anthropic /customers 的元数据行）。
一张卡只能有**一个**焦点：关键数字。焦点用 `--ink` 深色 + 左侧 3px 渐变竖标标记，
不靠放大字号硬抢。第一版四团小字（绿元数据/标题/灰胶囊/灰数字）互相抢，
结果是谁都不突出。

**④ 强调色必须过 WCAG AA,否则它不是"清爽"是"发虚"。**
`#12B98A` 白底只有 **2.52:1**，却被当成所有绿色文字色用 —— 这是
页面「看起来没做完」的物理原因，不是审美偏好。分工立规矩：
- `--ca-green #12B98A`：**只许用于图形**（渐变条、竖标、箭头描边、focus 轮廓）；
- `--ca-green-ink #097268`：**所有绿色文字**（白底 5.80、雾底 5.16）；
- `--ca-mut-ink #616A64`：**12~13px 小字灰**（白底 5.59、雾底 4.97）。
  原 `--ca-mut #7C857F` 只有 3.38~3.81，够大字不够小字。

改样式后**必须用实测计算色复算对比度**，不能只查源码：
CSS 压缩会改写颜色写法，grep 十六进制会漏。
用 Playwright 读 `getComputedStyle(el).color` + `fontSize`，
按字号选阈值（≥18.66px 用 3.0，其余 4.5）逐项判定。

**⑤ 斑马纹要在改完之后重新数一遍。**
给索引区加雾底后，它下游的每一段底色都平移一格 ——
本次就撞出「for-park 雾底紧跟 FAQ 雾底」的连续同底。
改任何段落背景后，抓渲染 HTML `grep -o 'class="ca-band[^"]*"'` 核一遍交替。

**验证顺序（缺一不可）：**
`cases:tags` → `cases:lint` → `cases-visual-check.py` → `next build` →
渲染 HTML 核内链数与标签词 → **实测色对比度审计** → 斑马纹核验 →
桌面 1440 + 手机 390 截图**自己先看一遍**（第一版的列不对齐、
第一版的孤儿卡片，都是只有看图才发现的，代码审查看不出来）。

**standalone 预览的两个坑（浪费过大量时间，务必先查）：**
- `output:"standalone"` 下必须手动同步 `.next/static` 与 `public` 到
  `.next/standalone/`，且**目标目录要先 `rm -rf`** —— 否则 `cp -a` 会拷成嵌套子目录，
  文件数翻倍而请求 404/500。拷完比对 `find|wc -l` 两边相等。
- 起服务前**必须确认端口真的空闲**（`ss -ltnp` 取 pid 后 `kill -9`）。
  端口被旧进程占着时新进程只在日志里写 `EADDRINUSE` 然后退出，
  页面照样能打开、返回 200，但你看到的是**旧构建** ——
  曾因此把「CSS 完全没加载」误判成 CSS 写错。
  判据：核对 `/cases` 引用的每个 CSS chunk 是否都返回 200。
