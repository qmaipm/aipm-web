# 客户案例页 Wording ＋ 页面设计审计报告

审计日期：2026-07-25 ｜ 审计对象：`/cases` 列表页 ＋ 11 个案例详情页
方法：全量文本量化分析（字数、句长、词频、模板化痕迹）＋ 1440×900 / 390×844 实测渲染布局 ＋ 6 家 AI 公司案例页对标

---

## 摘要（TL;DR）

你的直觉是对的，而且能被量化。三个结论：

**1. 信息密度不是「偏大」，是超标 2 倍。** 单篇平均 2,476 字，读完约 7 分钟。对标 Anthropic / OpenAI 案例页（600–900 英文词，3–4 分钟），你的案例页是它们的 **2 倍长**。更关键的是：**42% 的句子超过 60 字，20% 超过 80 字**，最长一句 228 字。中文读者在 60 字以上的句子里会失去主谓宾的追踪能力。

**2. 排版有一个硬伤级 bug：正文行宽 1096px = 每行 64 个汉字。** 排版学公认的舒适阅读行宽是 **每行 30–40 个汉字**（英文 50–75 字符）。Anthropic 实测是 715px / 20px = 每行 36 字符。你的正文行宽是它的 **1.8 倍**。这一条足以单独解释「读起来累、抓不住重点」——读者每读完一行，眼睛要横扫 1096px 再回到行首找下一行，极易串行。**这是本次审计中投入产出比最高的一处修改。**

**3. Wording 最大的问题不是「奇怪」，是「AI 缺席」。** 11 篇里，读者要读到正文 **33% 的位置**才第一次见到 FMClaw/AI 出场（医院篇更是到 **94%**）。而「AI 在里面做了什么」几乎从不被具体描述——它被写成一个笼统的「接管了」「跑完了」。对标 Anthropic：第 2 屏就是「Claude 做了这 7 件事」的清单，动词具体到「classifies / triggers / extracts / builds」。

**行宽这一条要展开说。** `.cf-sec-body{max-width:none}` ＋ `.wrap{max-width:1160px}` 导致正文直接铺满 1096px。CSS 里其实是有意识做过窄栏约束的——`.cf-lead{max-width:44ch}`、`.cf-step-d{max-width:58ch}`、`.cf-voice{max-width:26ch}` 都限了宽，**唯独承载 90% 阅读量的正文段落没限**。这更像是一处遗漏，而不是设计决策。

### 1.4 Hero 区信息堆叠

以医院篇为实测（Hero 高 1101px，占满整个首屏）：

```
面包屑 → 行业·规模·地区 → H1(32字, 4行) → summary(190字, 7行)
→ 3 个大数字面板 → 采用产品 → 发布/更新日期
```

**7 层信息，190 字的摘要。** 而 Anthropic 的 Hero 只有：`Case study` 标签 → H1 一句话（含结果）→ 4 个元数据 chip → 2 个大数字。摘要留到正文第一段。

问题在于：`summary`（190 字）说完了整个案例，然后 `CaseWins`（6 条，约 219 字）**又说了一遍**，然后正文（1,354 字）**再说第三遍**，最后 FAQ（952 字）**说第四遍**。

### 1.6 文风的「个人腔调」过载

全站 14,673 字正文里：

| 修辞习惯 | 次数 |
|---|---|
| `——` 破折号 | **76 次**（平均每篇 7 次） |
| `「」` 直角引号 | **54 对** |
| 「不是…而是…」句式 | **17 次** |
| 「第一次」 | 13 次（分布在 8/11 篇） |
| 「说不清 / 说得清」 | 13 次 |
| 「不再…」 | 21 次（8/11 篇） |
| 「…变成…」 | 18 次（8/11 篇） |

**这是问题的第二个根源。** 破折号平均每篇 7 次，意味着几乎每段都有一次「插入补充」。中文里破折号是**打断**——读者读到破折号，主句被挂起，要读完插入语再回来接。一篇 7 次打断 ＋ 平均 57 字的长句，叠加起来就是你感受到的「奇怪」。

「不是 A，而是 B」用了 17 次，也是同一个问题：它是一个**修正式**句型，先给一个错误答案再纠正。偶尔用是漂亮的，用到 17 次，读者会觉得作者一直在跟自己辩论。

跨案例还有一批复用的**签名短语**：「无感完成」（3 篇）、「配置成套」（3 篇）、「认真干活的人，干了就是干了、说得清、赖不掉」（metro / fmclaw 近乎逐字重复）、「人真到了那个位置，才填得了那张单」（3 篇）。单篇看是金句，连读三篇就成了模板。

### 1.8 章节标题的一致性

`eyebrow`（小标签）四段结构非常统一：**启盟帮 X 实现了 → 客户面临的问题 → 接入之后 → 结果**。这一点是**优点**，跨案例可预期。

但两处问题：
1. 第一个 eyebrow 有 11 种写法：「启盟帮这家医院实现了」「启盟帮这条地铁线实现了」「启盟帮这座工厂实现了」「启盟帮这家共享办公巨头实现了」…… 这种「量词秀」没有信息增量，反而让本该稳定的锚点变得不稳定。
2. `title`（大标题）常常是**第二个金句**而不是**结论**。例如「一个真正跑起来的智慧园区，长这样」「不是接了几件事，是把一整套管理工作系统化」——都是修辞，不是可扫读的信息。读者跳读章节标题时，得不到任何事实。

## 第二部分：他们怎么写（6 家对标）

### 2.1 Anthropic — 结构最值得抄

`anthropic.com/customers/advantage-solutions`、`/eve-legal`

```
[Case study | Claude 标签]
H1：Advantage Solutions gives frontline managers 70,000 hours back with Claude
     ↑ 主语=客户  谓语=获得的结果  数字  with Claude
[元数据 chips] Industry / Company size / Product / Partner / Location
[2 个大数字] 70,000+ hours redirected · Scaled from 150 to thousands
[1 段公司介绍 —— 只有 4 句]
[「With Claude, X 做到了：」7 条 bullet]  ← 第 2 屏就给全部结论
--- 以下是正文，读者可选读 ---
H2 Turning scattered AI pilots into operational scale   (问题)
H2 Choosing Claude, starting at the top                 (为什么选 / 怎么落地)
[pull quote 引言]
H2 70,000 hours back, and a path to enterprise scale    (结果)
H2 Looking ahead                                        (下一步)
[结尾大引言]
```

**可直接借鉴的 5 点：**
1. **H1 公式 = 客户 + 动词 + 量化结果 + with Claude**。产品名一定在标题里。
2. **元数据做成 chips**（行业/规模/产品/地区），不是一行灰字。可扫、可筛。
3. **「With Claude, X:」bullet 清单紧跟 Hero**，读者 15 秒内拿到全部结论，正文变成「想深究再看」。
4. **正文每段 3–5 句，句子短**。产品动作用具体动词（classifies / triggers / extracts）。
5. **两处引言**：中间一处、结尾一处，且引言人有职位。你已经做了一处，可以加一处收尾。

### 2.2 OpenAI — 人物驱动叙事

`openai.com/index/lowes/`、`/bbva/`

- 大量**具名高管发言**（CDIO、SVP Digital Commerce、SVP Store Operations 各一位），配头像照片。案例读起来像一篇报道，不像一份说明书。
- **产品被拟人化并命名**：Mylow / Mylow Companion，各一句话定义。读者记得住「那个叫 Mylow 的东西」。
- **真实的用户提问原话**做成 bullet：「For someone with kids, what's the best paint for a high-traffic area?」——一秒说清 AI 在做什么。
- 结尾必有 **"Results at a glance"** 数字清单 ＋ **"Leadership lessons"** 6 条方法论（BBVA 篇）。后者是给「想复制」的读者的，价值极高。

**对你最有用的一条**：**放一段真实的输入/输出样例。** 例如群消息报修那篇，完全可以放一个「员工在群里说了什么 → FMClaw 识别出的字段 → 生成的工单」的三格图。这比 1,268 字的描述有效 10 倍。

### 2.3 Sierra — 极简、纯故事

`sierra.ai/customers/sonos`

- 全篇几乎没有数字，靠**客户高管的完整叙述**推进（Dharam Rai, VP of CX 贯穿全文）。
- 关键做法：**先讲客户自己的业务指标**（time-to-music、Customer Effort Score），再讲 AI 如何影响它。AI 是配角，客户的经营语言是主角。
- 结构极短，5 个小节，每节 2–3 段。

**启示**：你的「客户原声」只有一句，而且没有具名（「该项目运营负责人」）。脱敏是必要的，但可以给到**职级 ＋ 从业年限**（「做了七年物业的项目负责人」），可信度会显著上升——south-china 篇正文里其实已经有「项目负责人做物业已经七年」这个细节，但没有被用在引言署名上。

## 第三部分：改进建议（按 ROI 排序）

### P0 — 一天内可做完，收益最大

**① 给正文加行宽约束**（预计单这一条就能解决 40% 的「读起来累」）

```css
/* article.css */
.cf-sec-body > p { max-width: 38em; }   /* 约 38 个汉字/行，从 64 降到 38 */
.cf-sec-body     { max-width: 780px; }
```
配套把正文字号从 `17px` 提到 `18px`，行高 `1.8` 保持。

**② 拆掉超长句**（先处理 >80 字的 51 句，尤其 south-china 那 3 句）
- 228 字的「四个 Agent」句 → 改成 `CaseFlow` 组件（代码里**已经存在但从未被使用**，`_CaseShell.tsx:38`）的 4 步编号列表。
- 174 字的「三层能力」句 → 改成 `CasePoints` 三张卡片（组件同样已存在未使用）。
- 152 字的政策引用 → 用 `.cf-note` 虚线框（样式已存在，`article.css:188`）单独呈现。

> 你的组件库里 `CasePoints` / `CaseFlow` / `.cf-note` / `.cf-cmp`（对比表）**全都写好了但一次都没在案例页里用过**——11 篇全是 `CaseWins` ＋ 纯 `<p>`。这是排版单调的直接原因。

**③ 削减破折号与「不是…而是…」**
- 破折号 76 → 目标 ≤ 25（每篇 ≤ 2 次）。多数可以直接改成句号断句。
- 「不是 A 而是 B」17 → 目标 ≤ 6（每篇最多 1 次，留给最关键的那个转折）。

### P1 — 一周内，结构性改善

**④ 每篇加一句「AI 到底做了什么」的具体描述，且提前到正文 20% 以内**

在「接入之后」段的开头，用 `CaseFlow` 给一条**可视化的动作链**，动词必须具体。例：

> 群报修案例：
> `01 抓取` 平台 Bot 7×24 读取群消息与图片
> `02 判别` 判断这条是不是报事（而非闲聊）
> `03 抽取` 识别地点 / 报事人 / 时间 / 事件类型四个字段
> `04 读图` 对图片做语义识别，归入事件类型
> `05 测情绪` 检出不满与催促，标记升级
> `06 派单` 按规则派给工程师，同时回执报事人

这一块目前是 3 段共 700 字的散文。改成 6 步流程后，**读者 8 秒 get 到 AI 在做什么**，而且和 Anthropic 的写法对齐。

**特别提醒**：medical（2/24 句提 AI）和 gigafactory（1/23 句）两篇**必须重写**，否则读者读完不知道这跟 AI 有什么关系。

**⑤ 重构 Hero，消除四重重复**

**⑥ H1 标题公式化**

现在 11 条标题里 2 条含 AI。建议统一为：**`客户身份：AI 做了什么，带来什么结果`**

## 第四部分：一页纸的写作规范（建议固化为 `CASES-STYLE.md`）

| 项目 | 硬性上限 |
|---|---|
| 单篇正文（不含 FAQ） | **≤ 900 字** |

| 正文行宽 | **≤ 38 em** |
| 正文配图 | **≥ 1 张** |
